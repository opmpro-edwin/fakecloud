fakecloud implements **807 of 807** AWS EC2 operations at 100% Smithy conformance — the complete control plane for the largest service surface in AWS. Request/response shapes, flattened `ec2Query` XML lists, field names, enum validation, and integer/length bounds are checked against AWS's own Smithy model on every commit.

## Supported features

- **Core networking** — VPCs (+ secondary CIDRs, tenancy), DHCP option sets, subnets (+ CIDR reservations), security groups (rules, references, VPC associations, per-interface quota validation), route tables, internet / egress-only / NAT gateways, and elastic IPs with transfer/move flows.
- **Compute** — `RunInstances` and the full instance lifecycle (start/stop/reboot/terminate/monitor), instance attributes, credit specifications, metadata + maintenance options, instance types, and topology. Key pairs and placement groups. **Instances are backed by real Docker/Podman containers** — `RunInstances` boots a container per instance, runs your user-data at boot, and maps start/stop/reboot/terminate onto the container lifecycle (falling back to a metadata-only control plane when no container runtime is present). `BlockDeviceMapping` EBS entries create attached volumes (size, type, source snapshot and encryption as asked), reported under the instance's `blockDeviceMapping`; terminating the instance deletes the `DeleteOnTermination` ones and detaches the rest. `RunInstances` with a `LaunchTemplate` (by `LaunchTemplateId` or `LaunchTemplateName`) resolves the version (`$Default` when none is given, `$Latest`, or a version number; an unknown template or version is `InvalidLaunchTemplateId.NotFound` / `InvalidLaunchTemplateName.NotFoundException` / `InvalidLaunchTemplateId.VersionNotFound`) and merges its `LaunchTemplateData` under the request's own parameters, as EC2 does: anything the request sets wins, a list the request sets (block-device mappings, network interfaces, security groups) replaces the template's, tags merge per resource type with the request's value winning, and an instance-level subnet or security group applies to the template's primary network interface. Every field the launch path honors comes from the template too (image, type, key pair, security groups, network interface subnet / private IP / groups / public IP, user data, IAM instance profile, tags, metadata, monitoring, placement, EBS optimization, credit specification, CPU options, DNS name options, termination / stop protection, block-device mappings as real volumes), and the instance carries the `aws:ec2launchtemplate:id` / `aws:ec2launchtemplate:version` tags. Network interfaces beyond the primary one are created (or an existing one attached) at their device index, and deleted with the instance (or detached) on termination; `InstanceMarketOptions` Spot launches report `instanceLifecycle` `spot`; a fixed `PrivateIpAddress` needs a single-instance launch and an address not already in use (`InvalidIPAddress.InUse`). Auto Scaling and CloudFormation launch through the same path.
- **Storage** — EBS volumes (+ modifications, recycle bin), snapshots (+ copy, tier, lock, fast restores, block-public-access), AMIs (register/copy/deprecate/deregistration-protection), and EBS encryption defaults. An encrypted volume with no named key uses the account's EBS default key: the AWS-managed `aws/ebs` key for the region (a real KMS key, reported by ARN, as is `GetEbsDefaultKmsKeyId`) unless `ModifyEbsDefaultKmsKeyId` set another. `EnableEbsEncryptionByDefault` encrypts every new volume; snapshots inherit their volume's key, volumes created from an encrypted snapshot inherit its encryption, key and size, and `CopySnapshot` keeps the source key in-region or uses the default key when it newly encrypts.
- **Seeded public AMI catalogue** — every account starts with a small catalogue of public Amazon-owned (Amazon Linux 2, Amazon Linux 2023 x86_64/arm64, Windows Server) and Canonical-owned (Ubuntu 22.04/24.04) AMIs, just like a real account. `DescribeImages` honours the `Owner` param (`amazon` / `aws-marketplace` / `self` / account id) and `name` filters with `*` wildcards, so the standard Terraform `data "aws_ami"` pattern (`most_recent = true`, `owners = ["amazon"]`, a `name` glob) resolves to a real image instead of returning empty — and anything that chains off it (an `aws_instance`, an ELBv2 target-group attachment) can be planned.
- **Interfaces** — elastic network interfaces with attachments, permissions, IPv4/IPv6 address assignment, and prefix lists.
- **Edge / advanced networking** — network ACLs, VPC peering, VPC endpoints + PrivateLink (services, connection notifications), flow logs, launch templates (+ versions: `SourceVersion`, `SetDefaultVersion`, real version deletion, `$Latest` / `$Default` / number selection and `MinVersion` / `MaxVersion` on describe, and `GetLaunchTemplateData` derived from a running instance), spot requests / fleets / EC2 fleets, capacity reservations (+ fleets, cancellation and date-change quotes), reserved instances, dedicated hosts.
- **Transit Gateway** — the complete 74-op surface: gateways, attachments, route tables (+ associations / propagations / prefix-list refs), peering, Connect + Connect peers, policy tables, route-table announcements, multicast domains (+ group members/sources), metering policies, and Client-VPN attachments.
- **Site-to-Site & Client VPN** — customer gateways, virtual private gateways, VPN connections (+ routes / tunnels / device configs), VPN concentrators, and full Client VPN (endpoints, routes, authorization rules, Cedar authorization policies + device posture, target networks, connections, certificate/config export-import).
- **IPAM** — IPAMs, scopes, pools, pool CIDRs + allocations, resource CIDRs, address history, resource discovery (+ associations, discovered getters), BYOASN, BYOIP-to-IPAM, external resource verification tokens, policies (+ allocation rules / org targets), and prefix-list resolvers (+ targets / rules / versions).
- **Verified Access** — instances, trust providers (+ attach/detach), groups, endpoints, policies (group + endpoint), logging configuration, and client-config export.
- **Network Insights** — reachability paths + analyses and access scopes + scope analyses (content, findings).
- **Outpost / hybrid** — carrier gateways, CoIP pools + CIDRs, local-gateway route tables, routes, VPC + virtual-interface-group associations, virtual interfaces, and groups.
- **Access & diagnostics** — EC2 Instance Connect endpoints, fast launch, serial-console access, console output / screenshot, and password data. `GetConsoleOutput` returns the instance container's real console log (its combined stdout/stderr, including anything user-data printed at boot), base64-encoded as on AWS.
- **Cross-cutting** — tag specifications on create, `CreateTags` / `DeleteTags` / `DescribeTags`, `Filter.N` filtering, and `MaxResults` / `NextToken` pagination on every operation the model paginates (all 215 `Describe*` / `Get*` / `Search*` / `List*` operations with a `NextToken` input): `MaxResults` is checked against the model's range, `nextToken` is opaque and returned only when items remain, and a token fakecloud did not mint is rejected with `InvalidParameterValue`.

## Protocol

EC2 uses the `ec2Query` protocol: form-encoded requests and flattened-XML responses (no `<member>` wrapper, lower-camel element names, lowercase `<requestId>`, no `<Result>` envelope). Because EC2 declares no per-operation error shapes, fakecloud is lenient on not-found and validates only wire-observable negatives — missing required scalars, invalid enum values, out-of-range integers / `MaxResults`, and bad lengths.

## Introspection

- `GET /_fakecloud/ec2/instances` — list every fakecloud-managed EC2 instance across all account partitions with its control-plane metadata (`instanceId`, `imageId`, `instanceType`, `state`, `privateIp`, `publicIp`, `subnetId`, `vpcId`, `keyName`, `securityGroupIds`, `availabilityZone`, `launchTime`) plus `containerId` — the backing Docker container id or Kubernetes Pod name, or `null` when the instance runs metadata-only (no container runtime). Lets tests assert on instance state (and which container backs it) without re-parsing `DescribeInstances` XML. Exposed through every fakecloud introspection SDK — `fc.ec2().getInstances()` (Go/Java/TS/PHP), `fc.ec2.get_instances()` (Python), `fc.ec2().get_instances()` (Rust).
- `GET /_fakecloud/ec2/instance-networks` — inspect each instance's **real backing network**: the Docker/Podman network (`fakecloud-subnet-<id>`) or k8s NetworkPolicy (`fakecloud-ec2-<id>`) that backs it, its container IP, the `isolationBackend` (`docker`/`podman`/`kubernetes`/`none`), the `securityGroupEnforcement` mechanism (`nftables`/`networkpolicy`/`disabled`), and whether enforcement is currently `enforcementActive`. A debugging aid for "why can't X reach Y". Exposed through every introspection SDK — `fc.ec2().getInstanceNetworks()` (Go/Java/TS/PHP), `fc.ec2.get_instance_networks()` (Python), `fc.ec2().get_instance_networks()` (Rust).

## Instance metadata service (IMDS)

fakecloud serves the EC2 instance metadata service on `/latest/*` so an app that resolves credentials through IMDS (rather than static keys) runs unmodified. Point the SDK's IMDS client at fakecloud with `AWS_EC2_METADATA_SERVICE_ENDPOINT=http://<host>:<port>/` and the default credential chain resolves locally with no code change.

Both IMDSv1 (plain GET) and IMDSv2 (`PUT /latest/api/token` then GET with `X-aws-ec2-metadata-token`) are supported; fakecloud hands out a token but does not enforce it. Served paths: `meta-data/iam/security-credentials/` (role name) and `meta-data/iam/security-credentials/{role}` (credential JSON, from the same registered-credential cache as `/_fakecloud/credentials`, so it verifies under `--verify-sigv4`), `meta-data/iam/info`, `meta-data/instance-id`, `meta-data/placement/region`, `meta-data/placement/availability-zone`, and `dynamic/instance-identity/document`. The reported instance ID is set with `--imds-instance-id`. See the [Run an app unmodified](/docs/guides/instance-credentials/#instance-metadata-imds) guide.

**Inside an instance.** Code running in an instance's backing container reaches IMDS at the real address, `http://169.254.169.254`, with that instance's own answers: its instance ID, AMI ID, instance type, private IP (`meta-data/local-ipv4`), Availability Zone, identity document, and credentials for the role of the instance profile associated with it (`IamInstanceProfile` on `RunInstances`, or `AssociateIamInstanceProfile`; an instance without a profile has no `iam/` paths, as on EC2). A sidecar sharing the instance's network namespace redirects `169.254.169.254:80` to a proxy that forwards to fakecloud's per-instance IMDS (`/_fakecloud/ec2/imds/<instance-id>/latest/...`), the way the ECS runtime routes `169.254.170.2`; it works in private subnets too, and when fakecloud itself runs in a container. User-data waits for it (up to 60 seconds) before running, so a boot script that reads IMDS first thing finds it. The Kubernetes backend adds the same sidecar to the instance Pod. If the helper image can't be built or pulled, the instance instead gets `AWS_EC2_METADATA_SERVICE_ENDPOINT` pointing at its per-instance IMDS on fakecloud. The helper image is overridable with `FAKECLOUD_EC2_HELPER_IMAGE`.

**Load balancer targets.** An ELBv2 target group that routes to `i-...:<port>` reaches the port the instance opened, even though it opened it after boot: on first use fakecloud starts a small forwarder that publishes that port on the host, and the load balancer data plane and health checks connect through it. Forwarders go away when the instance stops or terminates, and nothing is forwarded to a stopped instance. With security-group enforcement on, a forwarder counts as a member of the load balancer's security groups, so an instance rule that admits only the load balancer's group admits it.

## VPC networking

On the Docker / Podman backend an instance's container sits in its VPC the way an ECS task's does (see [ECS VPC networking](/docs/services/ecs/#vpc-networking-dns-and-load-balancers)):

- **Addresses.** A subnet's network (`fakecloud-subnet-<id>`) has the subnet's CIDR block as its range, with the bridge at the base plus one (the VPC router's address). An instance gets the subnet's lowest free address (AWS reserves the first four and the last; network interfaces in the subnet, such as an ALB's, are skipped; a terminated instance's address is free again) and its container holds exactly that address, so `DescribeInstances`, IMDS `local-ipv4`, other instances and security-group rules all see the same one. A launch that does not fit in the subnet fails with `InsufficientFreeAddressesInSubnet`. Load balancer forwarders get addresses the engine picks from the upper half of the range. When the engine refuses the range (another network already uses an overlapping one, as two VPCs with the same CIDR would), the subnet's network gets a range the engine picks and its instances report the addresses they were given; the same happens to an instance whose address another container still holds.
- **Egress.** fakecloud has no NAT gateways, so, as for ECS tasks, a private subnet (no `0.0.0.0/0 → igw` route) reaches the internet through the engine's NAT like a public one: package mirrors, registries and fakecloud itself. `FAKECLOUD_EC2_ISOLATE_PRIVATE_SUBNETS=1` puts private subnets on `--internal` networks instead, with no route out: no internet, and no IMDS, VPC DNS or AWS endpoint either.
- **DNS.** With `--dns`, the instance resolves through its VPC's DNS server (the VPC CIDR's base address plus two, and `169.254.169.253`), which fakecloud's resolver answers: private hosted zones, alias records and load balancer names resolve as in the VPC, and every other name is forwarded upstream. The container's `/etc/resolv.conf` names the engine's embedded DNS (`127.0.0.11`), which forwards to the VPC resolver from inside the instance's namespace; `host.docker.internal` is pinned in its hosts file where the engine would otherwise have resolved it.
- **Load balancers.** With `--dns`, a TCP connection to an Application Load Balancer's private address on one of its listener ports goes to `FAKECLOUD_ELBV2_FRONTEND_HTTPS` / `FAKECLOUD_ELBV2_FRONTEND_HTTP`, else fakecloud's own ALB data plane, exactly as from a task. The routes follow load balancers created, changed or deleted while the instance runs, within about a second.

The IMDS sidecar installs these rules in the instance's namespace before user-data runs. The Kubernetes backend gets none of this (Pods use the cluster's network and DNS).

## fakecloud extensions for instances

These have no AWS equivalent; they let a workload that expects real AWS run on an instance against fakecloud. All are for the Docker / Podman backend.

- **AWS SDK environment.** With `FAKECLOUD_EC2_AWS_ENV=1`, every instance container starts with `AWS_ENDPOINT_URL` (fakecloud as the instance reaches it, e.g. `http://host.docker.internal:4566`) and `AWS_REGION` / `AWS_DEFAULT_REGION` (the instance's region), as ECS task containers get them. They are the container's environment, so user-data and every command run with `docker exec` see them. The same lines (`NAME=value`) are in `/etc/fakecloud/aws.env`, in place before user-data runs, for a process started with a clean environment (`su -`, `env -i`, a service manager): `set -a; . /etc/fakecloud/aws.env; set +a`. A script that guards the line with `[ -f /etc/fakecloud/aws.env ]` runs unchanged on EC2. Off by default: on EC2 an SDK finds the real endpoints itself.
- **Trust for a local CA.** With `FAKECLOUD_EC2_EXTRA_CA` naming a PEM CA certificate (a path fakecloud reads), or else the CA in `FAKECLOUD_ECS_EXTRA_CA` that tasks trust, every instance container gets `/etc/fakecloud-ec2/ca-bundle.pem` (the image's system roots followed by the CA, in place before user-data runs) and `SSL_CERT_FILE` pointing at it, the same bundle tasks get (see [ECS extra CA](/docs/services/ecs/#extra-ca-for-tls)).
- **The host's container engine.** An instance launched with the tag `fakecloud:container-engine` = `host` gets the engine socket of the host fakecloud runs its containers on, mounted at `/var/run/docker.sock`, so a build host can build and run images. fakecloud does not install a CLI: user-data installs what it needs (for example `dnf install -y docker` on Amazon Linux, for the client). The socket is Docker's `/var/run/docker.sock`, or Podman's API socket; `FAKECLOUD_EC2_HOST_ENGINE_SOCKET` overrides its path on the engine's host. Containers started through it are siblings of the instance on that host: outside the instance's VPC, publishing their ports on the host, and never tracked or removed by fakecloud. The tag is read when the instance's container is created.

## Network isolation

VPC/subnet/security-group/NACL metadata isn't just stored — fakecloud gives instances **real network isolation** backed by the container runtime:

- **Default VPC** — every account+region ships a default VPC (`172.31.0.0/16`) with an internet gateway, a main route table, one default subnet per AZ, a `default` security group, and a default NACL, exactly like AWS. `RunInstances` with no `SubnetId` lands in the default subnet and attaches the `default` security group.
- **L3 isolation (Docker/Podman)** — each subnet gets its own daemon network (`fakecloud-subnet-<id>`, with the subnet's CIDR block as its range; see [VPC networking](#vpc-networking)); instances in the same subnet share a bridge and can talk, while instances in different VPCs/subnets land on different bridges and **cannot route to each other**. Private subnets (no `0.0.0.0/0 → igw` route) reach outside through the engine's NAT, as ECS tasks do, unless `FAKECLOUD_EC2_ISOLATE_PRIVATE_SUBNETS=1` backs them onto `--internal` networks with no NAT to the host.
- **Security-group + NACL enforcement (Docker/Podman)** — when enabled, security-group and NACL rules are translated into an **nftables** ruleset applied on the host, so SG rules actually block/allow traffic. As on AWS, a packet between two instances must be allowed by the sender's egress rules **and** the receiver's ingress rules: the two are evaluated as independent gates (separate nftables base chains), so the default security group's allow-all egress never lets traffic past the receiver's ingress default-deny. This needs `CAP_NET_ADMIN` + `nft`, so it is **opt-in** via `FAKECLOUD_EC2_SG_ENFORCEMENT=1` and **degrades gracefully**: without the capability (CI, Docker Desktop, rootless podman) the rules are tracked but not enforced, with a one-time startup warning — L3 isolation still holds. The published image ships `nft` (plus `kmod`/`procps`, which it needs to load and enable bridge netfilter so same-subnet traffic is actually filtered); you only need to grant the capability and set the env var. With `docker run`:

  ```sh
  docker run -e FAKECLOUD_EC2_SG_ENFORCEMENT=1 --cap-add=NET_ADMIN \
    -p 4566:4566 -v /var/run/docker.sock:/var/run/docker.sock \
    ghcr.io/faiscadev/fakecloud:latest
  ```

  or in `docker-compose.yml`, uncomment the `cap_add: [NET_ADMIN]` and `FAKECLOUD_EC2_SG_ENFORCEMENT` lines in the shipped compose. Confirm it took effect via `GET /_fakecloud/ec2/instance-networks` — `securityGroupEnforcement` reads `nftables` and `enforcementActive` is `true` when active.
- **Kubernetes** — on the k8s backend, isolation is expressed as **NetworkPolicy** objects (one per instance, derived from its security groups) and enforced by the cluster CNI. fakecloud detects the CNI (Calico/Cilium enforce; kindnet does not) and warns when NetworkPolicy won't be enforced, but always creates the policies.
- **Compose interop** — to let your own containers reach an instance by its private IP, attach them to the instance's subnet network: `docker network connect fakecloud-subnet-<id> <your-container>` (find `<id>` via `/_fakecloud/ec2/instance-networks`). Cross-VPC traffic stays isolated by design.

## Known limitations

- **Instances run as containers, not VMs** — `RunInstances` boots a real container per instance (Amazon Linux by default, overridable via `FAKECLOUD_EC2_DEFAULT_IMAGE`; a cached image is used as is, and a missing one is pulled first with transient registry failures such as `429 Too Many Requests` retried) and runs user-data at boot, but it is a container, not a full virtual machine: no kernel modules, no nested virtualization, and the instance type / EBS sizing is metadata only. The container runs as a local Docker/Podman container by default, or as a **native Kubernetes Pod** when `FAKECLOUD_EC2_BACKEND=k8s` (or the global `FAKECLOUD_CONTAINER_BACKEND=k8s`) is set — mirroring the Lambda/ECS/RDS/ElastiCache backends, so fakecloud running inside Kubernetes needs no Docker daemon. On the k8s backend a stopped instance's Pod is deleted and recreated on start (instances are not persistent disks). `AttachVolume` and `DetachVolume` check what EC2 checks (the instance exists and is not terminated, the volume is `available` and in the instance's availability zone, the device is a valid one not in use); with `FAKECLOUD_EC2_MOUNT_VOLUMES=1` an attached volume is mounted in the instance's container at its device name, as a directory rather than a block device, and keeps its data from one instance to the next (see [Configuration](/docs/reference/configuration/)). When no container runtime is available at all, the control plane degrades to a metadata-only instance so every API call still succeeds.
- **A handful of model operations are absent from the vendored AWS SDK** (`DescribeIpamPoolAllocations`, `ModifyIpamPoolAllocation`, the capacity-reservation cancellation-quote and date-change-quote pairs, and the `AttachImageWatermark`/`DetachImageWatermark` AMI watermark pair). They are implemented and conformance-probed via raw `ec2Query`, and graduate to typed SDK calls on the next SDK refresh.
- **Security-group / NACL packet filtering needs host privileges.** Real enforcement (above) requires `CAP_NET_ADMIN` + `nft` on Docker/Podman, or a NetworkPolicy-enforcing CNI on Kubernetes. Where neither is available the rules are stored and returned faithfully but tracked-only; L3 (per-subnet/VPC) isolation still applies. ICMP and IPv6 rules are modeled best-effort. On Docker/Podman, fakecloud enables bridge netfilter (`net.bridge.bridge-nf-call-iptables`) so same-subnet traffic is actually filtered.
- **Enforced security-group source matching uses real container IPs.** An instance's container holds its VPC address (see [VPC networking](#vpc-networking)), so an enforced rule keyed on a VPC CIDR matches peer instances. Where a subnet's network could not take the subnet's range (an overlapping network), its containers have engine-assigned addresses outside the VPC's CIDR, and only `0.0.0.0/0` and **referenced security groups** (which resolve to member instances' real IPs) match as intended. Metadata (`DescribeSecurityGroups`) is unaffected; this only concerns the optional packet-filtering path.
- **Subnets of one VPC do not reach each other, and instances and ECS tasks do not reach each other directly.** Each subnet and each `awsvpc` task has a network of its own; on AWS the VPC's local route connects them. Between subnets, and between instances and tasks, go through a load balancer.
